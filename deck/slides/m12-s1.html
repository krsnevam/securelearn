Real case · Sep 2025

The first malicious MCP server

What happened

Koi Security found “postmark-mcp” on npm, a lookalike of a legitimate email MCP server. After 15 clean versions, an update quietly sent a blind copy of every email to the attacker. Teams that auto-updated never noticed.

Your situation: Developers have installed 60 MCP servers from public registries. None is pinned to a version, and none has an owner.

Your call · 15 min

  1. Which servers stay, and who decides?
  2. What rules apply to versions and updates?
  3. How do we check a publisher is genuine?

Source: Koi Security research, September 2025

MODULE 12

RAG & MCP Security

6 of 10

Concept tested: the MCP rug pull; trust earned by early clean versions was then abused. Model answer. 1) Freeze new installs, inventory all 60, and keep only servers with a business owner, a clear purpose and an acceptable publisher; the rest are removed. 2) Pin exact versions; every update goes through review (diff the tool descriptions and behaviour) before rollout; no auto-update. 3) Prefer official servers published by the vendor itself, verify the publisher's identity and repository, and route all MCP traffic through a gateway that logs calls. Leadership point: one line of code turned a helpful tool into a silent data leak, so MCP servers need supplier-level vetting.
